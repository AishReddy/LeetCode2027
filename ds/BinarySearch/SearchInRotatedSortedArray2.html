Search in Rotated Sorted Array II

With Duplicates — LC 33 + one extra case

medium O(n) worst case O(log n) average
Problem

Same as Search in Rotated Sorted Array, but the array may contain duplicates. Return true if target exists, false otherwise.

⚠ Duplicates break the sorted-half identification. When nums[left] == nums[mid] == nums[right] you can't tell which half to search — both look identical.
⚡ Fix: when all three are equal, safely shrink both ends by 1 (left++, right--) and try again. Everything else is identical to LC 33.
Why Duplicates Break LC 33
In LC 33, you identify the sorted half with nums[left] <= nums[mid]. But consider:
nums = [1, 1, 1, 3, 1], target = 3
left=0, right=4, mid=2
nums[left]=1, nums[mid]=1, nums[right]=1
nums[left] <= nums[mid] ✓ → "left half sorted" — but WHERE is 3?
Could be left half [1,1,1] or right half [3,1] — impossible to tell
When nums[left] == nums[mid] == nums[right], both ends are the same value — they give you zero information about which side the rotation is on. The only safe move is to eliminate one from each end.
Approach — LC 33 + Duplicate Case
1
Found? nums[mid] == target → return true.
2
Duplicate case (new!): nums[left] == nums[mid] == nums[right] → can't determine sorted half → left++; right--; — safe because neither endpoint equals target (we already checked).
3
Left half sorted: nums[left] <= nums[mid] → range check target in [left…mid) → shrink accordingly.
4
Right half sorted: → range check target in (mid…right] → shrink accordingly.
5
Loop exits → return false.

Complexity Analysis
Time Complexity
O(n) worst
Worst case: all duplicates e.g. [1,1,1,1,3,1,1] — every iteration just does left++, right-- → degrades to linear scan.
Space Complexity
O(1)
Three variables only: left, right, mid.
Average case is still O(log n) — duplicates only cause linear degradation when the array is mostly the same value. In typical inputs the binary halving still dominates.

Why left++ and right-- are safe: We already checked nums[mid] == target (false) and we know nums[left] == nums[mid] == nums[right], so neither endpoint equals the target — safe to skip.
Java Solution
class Solution {
    public boolean search(int[] nums, int target) {
        int left = 0, right = nums.length - 1;

        while (left <= right) {
            int mid = left + (right - left) / 2;

            if (nums[mid] == target) return true;

            // ── NEW: duplicates block decision ──────────────────
            if (nums[left] == nums[mid] && nums[mid] == nums[right]) {
                left++;
                right--;
            }
            // ── same as LC 33 below ─────────────────────────────
            else if (nums[left] <= nums[mid]) {          // left sorted
                if (target >= nums[left] && target < nums[mid])
                    right = mid - 1;
                else
                    left = mid + 1;
            } else {                                      // right sorted
                if (target > nums[mid] && target <= nums[right])
                    left = mid + 1;
                else
                    right = mid - 1;
            }
        }
        return false;
    }
}
The only addition over LC 33
if (nums[left] == nums[mid] && nums[mid] == nums[right]) {
left++; right--;
}
Everything else — the left/right sorted half logic — is identical.
Key Insight
One rule: when nums[left] == nums[mid] == nums[right], the boundary values are useless — they can't tell you which side the rotation is on. Shrink both ends by 1 and retry.

Why this costs O(n) in worst case:
[1, 1, 1, 1, 1, 1, 2] target = 2
Every iteration: left++, right-- → 6 iterations just to shrink
Interview checklist:
1. Check nums[left] == nums[mid] == nums[right] first (before sorted-half check)
2. left++; right--; — shrink both, not just one
3. Return boolean, not index
